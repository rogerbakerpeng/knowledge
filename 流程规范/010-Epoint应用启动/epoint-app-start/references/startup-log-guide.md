- Started FrameEsfApplication in 167.577 seconds (JVM running for 324.657)。

- Starting ProtocolHandler ["http-bio-8081"]。
- LicenseInstall 输出验证成功，机器码与文件名已脱敏。
- 本次会话随后实际验证登录页、交易乙方身份、市场主体库首页数据加载成功。参考摘要 自身不证明任何新实例的登录结果。

## 启动耗时预期与等待策略

### 参考案例实测

以下为同一次启动的日志时间，日期为 2026-10-25。起点是首条可见 JRebel 日志，早于它的 JVM 创建、Maven 准备耗时不包含在内。

| 阶段 | 时间 | 距首条 JRebel 日志 |
|---|---|---|
| 首条 JRebel 日志 | 21:54:56 | 0 |
| Spring 激活 normal 配置 | 21:57:49 | 约 2 分 53 秒 |
| Root WebApplicationContext 初始化完成 | 21:58:49 | 约 3 分 53 秒 |
| Started FrameEsfApplication | 22:00:16 | 约 5 分 20 秒 |
| 后续组件、缓存、任务及 Servlet 初始化完成 | 22:08:56 | 约 14 分钟 |
| Tomcat Starting ProtocolHandler，8081 开始监听 | 22:08:57 | 约 14 分 1 秒 |
| 授权验证成功 | 22:09:04 | 约 14 分 8 秒 |

因此本案例的日志启动基线为 **约 14 分钟**，不是 Spring 输出的 167.577 秒。该行 JVM running for 324.657 也只代表当时 JVM 已运行约 5 分 25 秒。会话随后确认登录和首页可用，但参考摘要 没有浏览器验收时间，不能把 14 分钟写成“首页已验证”的精确耗时。

### 启动前如何告知用户

- **依赖齐全、配置已知的同类工程**：先预留 10–20 分钟用于启动与就绪检查；这是根据本案例给出的安排预算，不是所有 Epoint 工程的固定时限。
- **全新工程**：上述预算之外，还要增加下载依赖、本地模块编译安装、IDEA 导入和 JRebel 配置时间。先报告准备阶段进度，依赖与编译结束后再开始计算应用启动耗时；网络慢或缓存需修复时单独说明，不能把全部过程笼统承诺为 10–20 分钟。
- **后续重启**：未积累本机实测前仍预留 10–20 分钟，不假定缓存就一定能缩短到几分钟。记录最近成功耗时，按工程和机器更新预算。
- 建议启动提示：“依赖已准备好，本次启动预计 10–20 分钟；参考工程约 14 分钟完成监听和授权。最终以登录页及所需首页检查为准。”

### 等待与排查节点

- 0–5 分钟：参考中主要为 JRebel、类扫描和 Spring 初始化；不因尚无监听端口就判定失败。
- 5–15 分钟：Spring Started 之后可能仍有组件脚本、缓存、任务、Servlet 初始化；持续观察新日志，不因 Started 就提前宣布成功。
- 15 分钟仍未就绪：有新的初始化进展且无阻断异常，可以继续等待并更新预期。
- 20 分钟仍未就绪：主动检查当前阶段、进程 CPU/线程、端口、数据库/Redis/远程调用，说明已用时和具体等待点；时间超出预算不等于必须重启。
- 任一阶段连续 3–5 分钟没有新日志：先做只读诊断，检查线程及外部 I/O；静默本身不能证明卡死。若超过 30 分钟且仍无有效进展，应明确报告阻塞证据与下一步，避免无限等待或循环重启。
- 缺类、上下文失败、端口冲突等明确阻断异常出现时立即定位，不等满预算。修复后的新启动重新计时，保留上次失败原因和日志。
- 启动等待期间保持简短进度沟通，说明已用时、当前阶段与下一检查点；单次阻塞等待不超过 60 秒，避免长时间无反馈。

记录四个独立时间：准备开始/完成、JVM 启动、端口监听、登录及首页验证完成。最终报告准备耗时、应用启动耗时、总耗时和验证范围；缺少时间证据时写“约”或“未记录”，不推算成实测结果。

## 分级判读
| 类别 | 日志特征 | 处理 |
|---|---|---|
| 启动阻断 | Application run failed、Bean 创建失败且有缺类/缺方法、Error listenerStart、上下文启动失败、端口绑定失败 | 找最深具体异常并修复；即使容器端口监听也未成功 |
| 可访问但功能阻断 | 请求时 NoSuchMethodError、授权验证失败、Redis AUTH/SELECT/PING 失败 | 不能因为首页骨架或 HTTP 200 就宣称可用 |
| 已知可继续观察 | Tomcat 7 扫描 module-info.class 的 Invalid byte tag 19 | 本例非终止；若整体上下文正常及业务验证通过可记录残留，不先盲目降级 gson/lombok |
| 已知条件性告警 | Bean 不经过全部后处理器、重复断路器实现、重复事件源标识、配置增强时机提示 | 结合后续是否成功；涉及当前功能仍需查证 |
| 数据质量/模块告警 | 模块重复编码、部门/用户兼职/码集/字段表的孤儿数据、当前实现未指定业务标识 | 本例成功后仍存在，记录并单独评估；不在启动任务中擅自修库 |
| 数据库升级脚本错误 | epoint_proc_alter、mysql_Frame.sql、更新脚本执行出错 | 本参考存在且后来可登录，但不归为永久可忽略；记录具体脚本/SQL原因，确认相关功能和数据库版本，再另行修复 |

线程泄漏、Illegal access: web application ... stopped already 常是上下文失败后的后果，优先找前面的首个根因。单独的“退出码 0”也可能是应用初始化失败后退出。

## 日志采集要求
记录应用/模块、时间、端口/PID、启动 POM、JDK/Maven、JRebel 是否单份加载、最终 URL 和验证范围。对外汇报不输出密码/token/license 内容。保留完整日志在本地；提供摘要时只引用关键片段。

inspect-log 输出只用于导航：不能把 knownConditionalWarnings 视为“永远忽略”，不能用正则工具代替浏览器验收，也不要把多次启动拼在一起的成功行归给最后一次失败实例。
