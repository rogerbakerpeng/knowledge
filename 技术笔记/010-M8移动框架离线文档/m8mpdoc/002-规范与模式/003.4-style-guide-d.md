# 优先级 D 的规则：谨慎使用 (有潜在危险的模式)

<div class="style-guide">

## 环境判断不完整 <span class="priority-a">潜在危险</span>

**移动设备 os 判断不完整，仅通过`if-else` 判断可能会导致错误的结果。**

过去在判断`安卓`、`iOS`操作系统时，常见的做法是通过 `if` 语句判断其中一个操作系统，而 `else` 语句默认处理其他所有情况。

但这种方式存在潜在风险，特别是在出现像鸿蒙（HarmonyOS）这样的新操作系统时。仅靠 `if-else` 结构判断可能会遗漏对新系统的支持，导致功能异常。

因此在判断时，明确区分每个可能的操作系统，并为未来可能出现的新系统预留判断逻辑。

<div class="style-example example-bad">

### 反例：

```js
if (ejs.os.ios) {
    // xxx
} else {
    // xxx
}
```

```js
jsApiList: [
    {
        moduleName: ejs.os.android ? 'com.xxx.xxx' : 'ZDYxxx',
    },
];
```

</div>
<div class="style-example example-good">

### 好例子：

```js
if (ejs.os.ios) {
    // xxx
} else if (ejs.os.android) {
    // xxx
} else if (ejs.os.harmonyOs) {
    // xxx
} else {
    // 处理未知操作系统
}
```

```js
jsApiList: [
    {
        moduleName: ejs.os.android ? 'com.xxx.xxx' : ejs.os.ios ? 'ZDYxxx' : ejs.os.harmonyOs ? 'xxx' : 'unknown',
    },
];
```

</div>

## 判断 APP 版本号 <span class="priority-a">潜在危险</span>

在产品开发过程，应该避免判断 APP 版本号进行功能的开关。项目 APP 版本号不一定与产品的版本号对应匹配的，容易造成潜在危险。

<div class="style-example example-bad">

### 反例：

```js
ejs.runtime.getAppVersion({
    success: function (result) {
        let version = result.version || '';

        if (version >= '4.4.2') {
            jsApiLists = [
                {
                    moduleName: ejs.os.android ? 'MobileshieldNewApi' : 'ZDEJSApi',
                },
            ];
        } else if (version > '3.1.1') {
            jsApiLists = [
                {
                    moduleName: ejs.os.android ? 'com.epoint.app.plugin.MobileshieldNewApi' : 'ZDEJSApi',
                },
            ];
        }
    },
});
```

</div>
<div class="style-example example-good">

### 好例子：

```js
// 根据具体的功能需求，使用更合适的判断 API
if (ejs.os.miniH5) {
    jsApiLists = [
        {
            moduleName: ejs.os.android ? 'MobileshieldNewApi' : ejs.os.ios ? 'ZDYxxx' : ejs.os.harmonyOs ? 'xxx' : 'unknown',
        },
    ];
} else if (ejs.os.ejs) {
    jsApiLists = [
        {
            moduleName: ejs.os.android ? 'com.xxx.xxx' : ejs.os.ios ? 'ZDYxxx' : ejs.os.harmonyOs ? 'xxx' : 'unknown',
        },
    ];
}
```

</div>

## 引入未使用的组件或文件 <span class="priority-a">潜在危险</span>

引入未使用到的组件影响代码可读性，也可能产生未知的副作用，增大代码体积，建议只引入必需的组件或文件，以保持代码简洁。

<div class="style-example example-bad">

### 反例：

```html
<template>
    <van-button basic>保存</van-button>
</template>
```

```js
import minirefresh from '@components/minirefresh';
import vanButton from '@components/button';
export default {
    components: {
        minirefresh, // 该组件并未用到
        vanButton,
    },
};
```

</div>
<div class="style-example example-good">

### 好例子：

```html
<template>
    <van-button basic>保存</van-button>
</template>
```

```js
import vanButton from '@components/button';
export default {
    components: {
        vanButton,
    },
};
```

</div>
<!-- 结束 -->

## 没有在 `v-if`/`v-else-if`/`v-else` 中使用 `key` <span class="priority-a">潜在危险</span>

**如果一组 `v-if` + `v-else` 的元素类型相同，最好使用 `key` (比如两个 `<div>` 元素)。**

默认情况下，Vue 会尽可能高效的更新 DOM。这意味着其在相同类型的元素之间切换时，会修补已存在的元素，而不是将旧的元素移除然后在同一位置添加一个新元素。如果本不相同的元素被识别为相同，则会出现[意料之外的结果](https://codesandbox.io/s/github/vuejs/v2.vuejs.org/tree/master/src/v2/examples/vue-20-priority-d-rules-unintended-consequences)。

<div class="style-example example-bad">

### 反例：

```html
<div v-if="error">错误：{{ error }}</div>
<div v-else>{{ results }}</div>
```

</div>
<div class="style-example example-good">

### 好例子：

```html
<div v-if="error" key="search-status">错误：{{ error }}</div>
<div v-else key="search-results">{{ results }}</div>
```

</div>

## `scoped`中的元素选择器 <span class="priority-a">潜在危险</span>

**元素选择器应该避免在 `scoped` 中出现。**

在 `scoped` 样式中，类选择器比元素选择器更好，因为大量使用元素选择器是很慢的。

<details>
<summary>
  <h4>详解</h4>
</summary>

为了给样式设置作用域，Vue 会为元素添加一个独一无二的 attribute，例如 `data-v-f3f3eg9`。然后修改选择器，使得在匹配选择器的元素中，只有带这个 attribute 才会真正生效 (比如 `button[data-v-f3f3eg9]`)。

问题在于大量的元素和 attribute 组合的选择器 (比如 `button[data-v-f3f3eg9]`) 会比类和 attribute 组合的选择器 (比如 `.btn-close[data-v-f3f3eg9]`) 慢，所以应该尽可能选用类选择器。

</details>

<div class="style-example example-bad">

### 反例：

```html
<template>
    <button>X</button>
</template>

<style scoped>
    button {
        background-color: red;
    }
</style>
```

</div>
<div class="style-example example-good">

### 好例子：

```html
<template>
    <button class="btn btn-close">X</button>
</template>

<style scoped>
    .btn-close {
        background-color: red;
    }
</style>
```

</div>

## 隐性的父子组件通信 <span class="priority-a">潜在危险</span>

**应该优先通过 prop 和事件进行父子组件之间的通信，而不是 `this.$parent` 或变更 prop。**

一个理想的 Vue 应用是 prop 向下传递，事件向上传递的。遵循这一约定会让你的组件更易于理解。然而，在一些边界情况下 prop 的变更或 `this.$parent` 能够简化两个深度耦合的组件。

问题在于，这种做法在很多*简单*的场景下可能会更方便。但请当心，不要为了一时方便 (少写代码) 而牺牲数据流向的简洁性 (易于理解)。

<div class="style-example example-bad">

### 反例：

```js
Vue.component('TodoItem', {
    props: {
        todo: {
            type: Object,
            required: true,
        },
    },
    template: '<input v-model="todo.text">',
});
```

```js
Vue.component('TodoItem', {
    props: {
        todo: {
            type: Object,
            required: true,
        },
    },
    methods: {
        removeTodo() {
            var vm = this;
            vm.$parent.todos = vm.$parent.todos.filter(function (todo) {
                return todo.id !== vm.todo.id;
            });
        },
    },
    template: `
        <span>
            {{ todo.text }}
            <button @click="removeTodo">
                X
            </button>
        </span>
    `,
});
```

</div>
<div class="style-example example-good">

### 好例子：

```js
Vue.component('TodoItem', {
    props: {
        todo: {
            type: Object,
            required: true,
        },
    },
    template: `
        <input
            :value="todo.text"
            @input="$emit('input', $event.target.value)"
        >
    `,
});
```

```js
Vue.component('TodoItem', {
    props: {
        todo: {
            type: Object,
            required: true,
        },
    },
    template: `
        <span>
            {{ todo.text }}
            <button @click="$emit('delete')">
                X
            </button>
        </span>
    `,
});
```
